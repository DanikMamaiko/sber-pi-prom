# Pre PI Planning

## Граница агрегата

Вкладка является частью агрегата PI-цикла и использует общую
`pi_cycles.version`. PostgreSQL хранит инициативы, исполнителей, трудозатраты,
канонический блок и порядок, публикацию и нормализованные запросы на привлечение.
Frontend хранит только последний read model, несохранённый ввод формы и UI-фильтры.

`GET /api/pi-cycles/{cycle_id}/pre-pi` возвращает готовый read model: метаданные
цикла, трайбы и команды с UUID/типами/компетенциями, справочник целей, списки
`planned` и `backlog`, полный список `initiatives`, допустимые действия и значения,
общую оценку, capacity по командам/трайбам и показатели техповестки. Все числовые
значения рассчитываются backend; нулевой знаменатель процента представлен `null`.

## Команды

- `PATCH .../pre-pi/initiatives/{initiative_id}` — атомарно изменяет разрешённые
  поля инициативы либо весь подграф исполнителей/трудозатрат/привлечений формы.
- `POST .../pre-pi/initiatives/{initiative_id}/move` — переносит инициативу между
  блоками или меняет её каноническую позицию через `before_id`.
- `DELETE .../pre-pi/initiatives/{initiative_id}` — удаляет инициативу с проверкой
  опубликованных зависимостей.
- `POST .../pre-pi/submit` — атомарно и идемпотентно публикует явно выбранные
  команды, создаёт/актуализирует цели и обрабатывает привлечения.
- `PUT .../pre-pi` сохранён как совместимый bulk-контракт для внешних клиентов;
  активный frontend его не использует.

Все команды принимают `expected_version`, блокируют строку PI-цикла, увеличивают
версию ровно один раз и возвращают read model после фактического чтения БД.
`version_conflict` и `cascade_confirmation_required` не повторяются frontend
автоматически. Возврат опубликованной инициативы требует `confirm_cascade: true`,
снимает публикацию и удаляет связанную цель в той же транзакции.

## Общие данные с вкладкой «Цели»

Цель/веха, метрика, AS IS, TO BE, гипотеза и редизайн находятся только в
`initiatives`. `pi_goals` хранит связь инициативы с командой и порядок. Поэтому
редактирование из «Целей» и Pre PI изменяет одну `Initiative`, без browser-sync и
копирования бизнес-данных.

## Привлечения

`initiative_attractions` содержит стабильный UUID, исполнителя-источник, целевую
инициативу, целевую команду, спринт, явный статус согласования и порядок. Backend
проверяет принадлежность циклу, спринт, компетенции, дубли и self-reference.
Read model отдельно возвращает `approval_status` и `visual_state`; UI не выводит
статус из цвета или полей другой инициативы.

## Frontend

Вкладка не содержит Pre PI seed, frontend-валидации обязательных полей,
capacity/tech-agenda расчётов, snapshot-autosave или прямых мутаций сохранённого
`state.issues`. После одной команды UI заменяет read model только успешным ответом.
При 409/422/500 прежний read model остаётся каноническим.
