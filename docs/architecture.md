# Архитектура MVP

## Цель

Собрать production-направленный MVP раздела PI-цикла без ролей, авторизации и Jira-интеграции. Прототип `pi-planning.html` используется как функциональная спецификация, но не переносится в новый проект как единый файл.

## Слои

### Frontend

Vanilla HTML/CSS/JS:

- статические файлы в `frontend/`;
- общение с backend только через REST API;
- состояние экрана хранится в JS-памяти браузера;
- источник истины для бизнес-данных - backend/Postgres.

`/api/pi-cycles` хранит только метаданные цикла. Нормализованные разделы имеют
собственные агрегатные API: `/setup`,
`/backlog-board`, `/pre-pi`, `/goals-board`, `/team-boards`, `/capacity`, `/program-board` и
`/risks-board`. После релиза B frontend не читает и не отправляет `snapshot`, не импортирует
старые бизнес-данные из sessionStorage, а backend отвечает 422 на это поле в write-запросах.
В `sessionStorage` остаются только настройки экрана; бизнес-данные PI-циклов там не хранятся.

Pre PI, командные доски, ёмкость и риски уже используют нормализованные `Initiative`,
`InitiativeExecutor`, `Story`, `WorkItem`, `PiCycleCapacityMember` и `Risk` как источник истины.
Размещение по спринтам/неделям, порядок стикеров и согласование сохраняются через агрегат
`/team-boards`; состав и серверные расчёты ёмкости — через `/capacity`; связи и геометрия
Program Board — через `/program-board`; общие и командные риски — через `/risks-board`.
Compatibility snapshot полностью удалён миграцией `20260728_0009`; frontend, модель БД,
Pydantic DTO и OpenAPI содержат только нормализованный контракт.

Вкладка «Бэклог» использует отдельный глобальный агрегат `BacklogBoardState`. Активный
frontend хранит только последний `/backlog-board` read model и UI-фильтры. Создание,
редактирование, удаление, перестановка и перенос выполняются отдельными командами;
успешный ответ полностью заменяет read model. Отложенного autosave, frontend-снимка,
демопосева и legacy API нет. Подробный контракт описан в `docs/backlog-tab.md`.

Миграция `20260728_0010` добавила optimistic locking. Все агрегаты одного PI-цикла используют
общую `pi_cycles.version`, поскольку изменение setup, Pre PI или командной доски может менять
связанные сущности других вкладок. Глобальный бэклог использует отдельную версию singleton-
строки `backlog_board_state`. Запись выполняется только после проверки `expected_version` под
row lock; конфликт возвращается как 409. Frontend отправляет собственные изменения
последовательно и не перезаписывает сервер автоматически после конфликта.

«Отправить на доски» выполняется одной транзакцией Postgres: сервер валидирует
Pre PI, создаёт `PiGoal`, меняет состояние инициатив и публикует привлечённые
задачи. Вкладка «Цели» и Pre PI редактируют одни и те же поля `Initiative`.

### Backend

FastAPI:

- REST API в `backend/app/api/`;
- доменная модель в `backend/app/models/`;
- DTO-схемы в `backend/app/schemas/`;
- расчёты PI-цикла в `backend/app/services/`;
- миграции схемы БД в `backend/alembic/`.

Схема БД управляется Alembic. Перед запуском API контейнер автоматически
выполняет `alembic upgrade head`; ручной `create_all` из lifespan удалён.

### Database

PostgreSQL:

- нормализованные сущности для PI-цикла;
- JSONB используется только там, где структура естественно словарная: трудозатраты по компетенциям, списки тегов, диапазоны недоступности;
- связи между сущностями сделаны через UUID foreign keys.

## Основной поток MVP

1. Создать или открыть PI-цикл.
2. Завести трайбы и команды.
3. Добавить инициативы в бэклог вручную.
4. Перенести инициативы в выбранный PI-цикл.
5. Уточнить цели PI.
6. Смотреть инициативы в Pre PI и Program Board.
7. Вести общие и командные риски.

## Что не входит в MVP

- авторизация и аутентификация;
- ролевая модель;
- Jira/JSW-интеграция;
- бюджетирование;
- сложный drag-and-drop как в прототипе;
- аудит изменений;
- realtime-совместная работа.
