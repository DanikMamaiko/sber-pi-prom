# Нагрузочное тестирование Program Board

## Что именно измеряет тест

Набор из 2000 стикеров создаётся напрямую в PostgreSQL через ORM приложения. Это не
тест скорости импорта или создания карточек пользователем. Он предназначен для проверки:

- времени и размера ответа `GET /api/pi-cycles/{cycle_id}/program-board`;
- CPU и памяти API/ PostgreSQL при построении проекции;
- времени построения DOM, загрузки CPU и прироста памяти браузера на VDI;
- фильтрации, масштаба, прокрутки, открытия карточки и перемещения стикера;
- поведения при нескольких одновременных пользователях.

Не используйте рабочий PI. Утилита по умолчанию создаёт отдельный `2099 Q4`, трайб
`Нагрузочный тест VDI-2000`, 20 команд и ключи вида
`LOAD-VDI-2000-000001`. Если указанный PI уже существует, но не содержит трайб этого
запуска, создание прекращается. Обход защиты возможен только явным параметром
`--allow-existing-cycle`.

Перед первым прогоном проверьте резервную копию БД и сначала выполните сценарий в
тестовом namespace.

## Создание данных

### Из новой версии API-образа

Модуль входит в production API-образ. Он использует уже смонтированные в под секреты и
не выводит строку подключения:

```powershell
kubectl -n sberpi exec deployment/sberpi-api -- `
  python -m app.tools.program_board_load create `
  --year 2099 --quarter Q4 --run-id VDI-2000 --count 2000 --teams 20
```

Повторный вызов идемпотентен: уже существующие ключи не дублируются. Команда должна
завершиться строкой `всего тестовых стикеров=2000`.

Проверка без изменений:

```powershell
kubectl -n sberpi exec deployment/sberpi-api -- `
  python -m app.tools.program_board_load status `
  --year 2099 --quarter Q4 --run-id VDI-2000
```

### Из текущего образа без пересборки

Если в уже развёрнутом образе модуля ещё нет, передайте скрипт на стандартный ввод
Python. Для Windows PowerShell 5 сначала включите UTF-8 для конвейера:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new()
Get-Content -Raw -Encoding UTF8 .\backend\app\tools\program_board_load.py | `
  kubectl -n sberpi exec -i deployment/sberpi-api -- `
  env PYTHONPATH=/app python - create `
  --year 2099 --quarter Q4 --run-id VDI-2000 --count 2000 --teams 20
```

Такой запуск создаёт отдельный Python-процесс внутри API-пода. Выполняйте его вне
рабочего пика и наблюдайте за лимитом памяти пода. Если корпоративные правила запрещают
`kubectl exec`, используйте отдельный Kubernetes Job на том же API-образе и с теми же
ConfigMap, Secret и NetworkPolicy labels.

Локально, при наличии разрешённого сетевого доступа к тестовой БД:

```powershell
python backend/seed_program_board_load.py create `
  --year 2099 --quarter Q4 --run-id VDI-2000 --count 2000 --teams 20
```

## Как измерять память VDI

Для сравнимого результата используйте одну и ту же версию VDI и браузера, одинаковое
разрешение экрана и новый профиль InPrivate/Incognito. Закройте остальные вкладки.
Сделайте не менее трёх прогонов и сравнивайте медиану, а не единичный максимум.

Запишите четыре точки:

1. браузер запущен, SberPI ещё не открыт;
2. пользователь вошёл, но Program Board не открыт;
3. Program Board `2099 Q4` полностью отрисован и простаивает 60 секунд;
4. после 5 минут прокрутки, фильтрации, открытия 20 карточек и 20 перемещений.

В Chromium-браузере откройте диспетчер задач браузера (`Shift+Esc`) и снимайте
`Memory footprint` именно строки вкладки SberPI. В DevTools откройте командное меню,
запустите `Show Performance monitor` и фиксируйте:

- `JS heap size`;
- `DOM Nodes` и `Documents`;
- `Event listeners`;
- CPU usage и Layouts/sec.

Полный расход браузера на чистой VDI можно дополнительно снимать PowerShell-командой
(замените `msedge` на `chrome`, если нужно):

```powershell
Get-Process msedge -ErrorAction SilentlyContinue |
  Measure-Object -Property WorkingSet64 -Sum |
  Select-Object @{Name='BrowserWorkingSetMiB';Expression={[math]::Round($_.Sum / 1MB, 1)}}
```

Главная величина — разница между точками 2 и 3. Разница между 3 и 4 показывает,
накапливается ли память при работе. После закрытия вкладки проверьте, возвращается ли
память процессу браузера; устойчивый рост от прогона к прогону указывает на возможную
утечку.

## Серверные измерения

Снимите базовую линию до открытия доски, затем наблюдайте во время одиночного и
многопользовательского прогона:

```powershell
kubectl -n sberpi top pods --containers
kubectl -n sberpi get pods
kubectl -n sberpi logs deployment/sberpi-api --since=15m
```

В DevTools на вкладке Network для запроса `.../program-board` запишите TTFB, полное
время, размер переданных данных и размер JSON после распаковки. Проверьте отдельно
первое открытие и обычное обновление страницы.

Если в кластере есть Prometheus, полезны максимумы и p95 по:

- working set, CPU и рестартам API/frontend-подов;
- latency и кодам ответа ingress для `GET .../program-board` и `PATCH .../position`;
- активным подключениям, CPU, I/O и медленным запросам PostgreSQL;
- сетевому объёму ответа на одного пользователя.

Текущий `PATCH` перемещения возвращает полную проекцию Program Board. Поэтому при 2000
карточках обязательно проверьте не только открытие, но и серию перемещений: это отдельный
нагруженный сценарий по CPU, памяти и сети.

## Матрица прогонов

Минимальная полезная матрица:

| Сценарий | Что фиксировать |
|---|---|
| 0 / 500 / 1000 / 2000 карточек, один пользователь | время ответа, размер JSON, время отрисовки, прирост RAM |
| холодное открытие и 5 повторных открытий | медиана и p95, стабильность памяти |
| фильтр владельца/исполнителя, масштаб, длинная прокрутка | CPU, long tasks, FPS, DOM nodes |
| 20 перемещений карточек | latency `PATCH`, объём ответа, рост RAM, ошибки 409/5xx |
| 10 / 25 / 50 одновременно читающих пользователей | p95/p99, CPU/RAM API и БД, ingress 5xx |
| два редактора одного PI | ожидаемые 409 optimistic locking, целостность позиций |
| 30 минут активной работы | накопление heap/working set и восстановление после закрытия вкладки |

Нагрузку HTTP увеличивайте ступенчато, с паузой между ступенями. Не включайте LDAP-login
каждого виртуального пользователя в основной сценарий чтения доски, если отдельно не
проверяете LDAP: иначе результат будет измерять доменную инфраструктуру, а не Program
Board. Критерии приёмки (допустимый p95, максимальная RAM VDI, доля ошибок и отсутствие
OOM/restart) зафиксируйте до запуска.

## Удаление тестовых стикеров

Сначала убедитесь, что выбран тот же `year`, `quarter` и `run-id`:

```powershell
kubectl -n sberpi exec deployment/sberpi-api -- `
  python -m app.tools.program_board_load status `
  --year 2099 --quarter Q4 --run-id VDI-2000
```

Удаление требует явного `--yes`:

```powershell
kubectl -n sberpi exec deployment/sberpi-api -- `
  python -m app.tools.program_board_load cleanup --yes `
  --year 2099 --quarter Q4 --run-id VDI-2000
```

Утилита удаляет только инициативы с префиксом данного запуска и связи, которые на них
ссылаются. Связи ORM удаляют исполнителей, истории и work items этих инициатив. Ссылки
целей и рисков обнуляются. PI и 20 справочных тестовых команд намеренно остаются: их
автоматическое каскадное удаление было бы опаснее точечной очистки данных. Финальный
`status` должен показать `стикеров=0`.
