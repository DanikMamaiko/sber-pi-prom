# Аудит действий пользователей

## Назначение

Backend регистрирует пользовательские вызовы API в таблице `audit_events` основной PostgreSQL-базы. Аудит
охватывает чтение и изменение данных, успешные и неуспешные входы, выходы, отказы в
доступе, ошибки валидации, конфликты версий, серверные ошибки и отмену выполняющегося
HTTP-запроса. Технический `/api/health` не считается пользовательским действием.

Бизнес-данные и аудит используют одно подключение, но разные миграционные цепочки:

- `DATABASE_URL`, `backend/alembic/` и `alembic_version` — бизнес-данные;
- `backend/audit_alembic/` и `audit_alembic_version` — таблица `audit_events`.

Пустой `AUDIT_DATABASE_URL` означает использование `DATABASE_URL`. Отдельное подключение
оставлено только для совместимости с прежними контурами.

## Состав события

`audit_events` хранит:

- UUID события и корреляционный `request_id`;
- UTC-время события, начала и окончания операции, длительность;
- сервис, компонент, окружение, hostname и IP хоста;
- имя пользователя и auth-provider;
- IP источника;
- стандартизированное действие, тип и идентификатор объекта;
- результат `success`, `failure` или `cancelled`;
- HTTP-метод, шаблон маршрута, фактический path и статус;
- безопасное описание, код ошибки и path-параметры.

Тела и значения query-параметров намеренно не сохраняются. Пароли, cookie и токены в
аудит не попадают. Для корреляции сессии сохраняется только SHA-256-хеш cookie.

## Определение IP

По умолчанию `source_ip` — адрес непосредственного TCP-клиента. Заголовок
`X-Forwarded-For` учитывается только когда непосредственный клиент входит в одну из сетей
`AUDIT_TRUSTED_PROXY_NETWORKS`. Это не позволяет внешнему клиенту подменить адрес простым
добавлением HTTP-заголовка.

`host_ip` можно явно задать через `AUDIT_HOST_IP`. Без настройки backend определяет адрес
своего hostname, что в Docker соответствует адресу контейнера.

## Отказ audit-БД

Запись выполняется после завершения бизнес-операции. Недоступность независимой audit-БД
не изменяет результат уже зафиксированной бизнес-транзакции. При ошибке событие целиком
пишется как структурированная запись `audit_fallback` в журнал backend, а повторные
подключения ограничиваются circuit breaker с интервалом `AUDIT_RETRY_SECONDS`.
Таймаут первичного подключения задаётся `AUDIT_CONNECT_TIMEOUT_SECONDS`.

Для production инфраструктурный сборщик логов должен забирать `audit_fallback`, иначе
между двумя независимыми PostgreSQL-базами невозможно обеспечить атомарность без
распределённой транзакции.

## Миграции и просмотр

Docker-контейнер API автоматически выполняет обе цепочки миграций. Вручную:

```powershell
cd backend
alembic -c audit_alembic.ini upgrade head
alembic upgrade head
```

Пример проверки последних событий:

```sql
SELECT occurred_at, username, source_ip, action, object_type, object_id, result, http_status
FROM audit_events
ORDER BY occurred_at DESC
LIMIT 100;
```

Публичного API чтения или удаления аудита нет.

## Передача в SIEM

Audit-БД является готовым источником для SIEM-коннектора. Прямая отправка пока не включена,
поскольку формат и транспорт должны предоставить ИБ: syslog/CEF, JSON/HTTP, Kafka или иной
корпоративный интерфейс. После согласования экспорт добавляется независимо от бизнес API,
используя `event_id` для дедупликации.
