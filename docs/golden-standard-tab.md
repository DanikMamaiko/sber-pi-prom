# Золотой стандарт вкладки PI-цикла

## Назначение

Вкладка «Данные PI-цикла» — эталон для остальных рабочих вкладок SberPI. Этот
документ фиксирует обязательный архитектурный контракт. Он относится к PI-циклу;
модуль бюджетирования в этот контур не входит.

Главный принцип: PostgreSQL и backend являются единственным источником истины.
Frontend отображает полученный read model, собирает пользовательский ввод и
отправляет команду. Он не принимает доменных решений, не рассчитывает бизнес-
показатели и не сохраняет бизнес-данные.

## Неподлежащие ослаблению инварианты

1. Одно действие пользователя соответствует одной backend-команде.
2. Команда и все её каскады выполняются в одной транзакции PostgreSQL.
3. Успешный ответ команды содержит полный актуальный read model вкладки.
4. UI после команды перестраивается только из ответа backend.
5. При сетевой ошибке или ответе с ошибкой бизнес-состояние UI не объявляется
   сохранённым и локальный draft не становится источником истины.
6. Перезагрузка и второй браузер показывают одно состояние из backend.
7. В browser storage нет данных PI-цикла, демоданных и бизнес-миграций.
8. Все расчёты, проверки, каскады, сортировка и нормализация выполняются backend.
9. Все изменяемые записи имеют стабильные UUID. Переименование не меняет UUID.
10. Конкурирующие изменения защищены общей версией агрегата PI-цикла.

## Граница агрегата и транзакция

Для вкладки «Данные PI-цикла» агрегат включает:

- дату старта и число спринтов;
- ПИРы;
- команды PI-цикла и их компетенции;
- варианты целей;
- теги;
- ссылки на эти сущности из инициатив, исполнителей, capacity и рисков.

`PUT /api/pi-cycles/{cycle_id}/data` принимает один снимок формы с
`expected_version`. Сервис блокирует PI-цикл, проверяет версию, валидирует весь
снимок, определяет каскады, применяет их и увеличивает версию ровно один раз.
Commit выполняется на API-границе. Частично применённая команда невозможна.

Если удаление или сокращение числа спринтов затрагивает связанные данные, backend
сначала отвечает `409 cascade_confirmation_required` и перечисляет последствия.
Повтор той же команды с `confirm_cascade: true` применяет основной результат и
все каскады атомарно. Frontend не вычисляет этот список сам.

Одновременные переименования внутри одной команды, включая перестановку имён двух
тегов или двух команд, должны поддерживаться по UUID. Временная техническая
перелинковка допустима только внутри серверной транзакции и не видна клиенту.

## Контракты backend

### Команда

Write DTO содержит только ввод пользователя, стабильные идентификаторы,
`expected_version` и при необходимости `confirm_cascade`. DTO запрещено подменять
неструктурированным snapshot или произвольным JSON состояния страницы.

Backend обязан:

- проверить принадлежность UUID выбранному PI-циклу;
- проверить уникальность и доменные ограничения;
- разрешить ссылки и вычислить каскады;
- выполнить изменения через доменный сервис;
- вернуть канонический read model из БД после `flush`;
- откатить всю транзакцию при любой ошибке.

### Read model

Read model готов к непосредственному отображению и содержит:

- данные цикла и актуальную `version`;
- стабильные UUID всех строк;
- готовые серверные даты и производные значения;
- канонический порядок коллекций;
- только данные, разрешённые контрактом вкладки.

Frontend не должен соединять несколько ответов в новый бизнес-снимок. Если экрану
нужна производная величина или дополнительная связь, она добавляется в read model.

### Ошибки

- `409 version_conflict` — состояние изменил другой клиент; UI перечитывает данные
  только по явному сценарию и не повторяет запись автоматически.
- `409 cascade_confirmation_required` — требуется подтверждение перечисленных
  backend последствий.
- `422` — команда не прошла структурную или доменную валидацию.
- `404` — агрегат или вложенная сущность не принадлежит выбранному циклу.

## Контракт frontend

Допустимое состояние frontend:

- последний read model, полученный от backend;
- временный draft полей текущей формы в памяти DOM/JavaScript;
- чисто визуальные настройки: активная вкладка, раскрытие блоков, фильтры.

Недопустимо:

- сохранять PI business data в `localStorage`, `sessionStorage`, IndexedDB или
  service-worker cache;
- использовать демоданные как fallback при ошибке API;
- выполнять бизнес-миграции в браузере;
- рассчитывать даты спринтов, каскады, capacity или доменные статусы;
- оптимистично изменять каноническое состояние до успешного ответа команды;
- собирать новый источник истины из устаревшего frontend state.

Поток экрана:

1. Открытие вкладки вызывает один запрос read model.
2. Рендер — чистая проекция этого ответа с сохранением дизайна прототипа.
3. Режим редактирования создаёт только несохранённый draft.
4. «Сохранить» отправляет одну bulk-команду.
5. При успехе `apply...View(response)` заменяет локальный read model и выполняет
   повторный render.
6. При ошибке сохранённый read model не меняется; UI показывает ошибку или запрос
   подтверждения.

## Эталонная структура кода

Реализация вкладки «Данные PI-цикла» разнесена по слоям:

- `backend/app/schemas/pi_cycle.py` — command/read DTO;
- `backend/app/api/pi_cycles.py` — HTTP-граница и управление транзакцией;
- `backend/app/services/pi_cycle_data.py` — доменная логика, read model и каскады;
- `backend/app/models/` — нормализованное состояние PostgreSQL;
- `frontend/index.html` — запрос, draft и отображение без доменной логики;
- `backend/tests/integration/test_pi_cycle_api.py` — транзакционные API-сценарии;
- `backend/tests/test_frontend_pi_data_contract.py` — архитектурные запреты frontend.

Для следующей вкладки следует сохранить эту структуру имён: отдельные `Read` и
`Command` DTO, один агрегатный GET, одна команда на пользовательское действие,
один доменный сервис и отдельные контрактные тесты frontend.

## Обязательная матрица тестов

### Unit

- граничные значения и доменные формулы;
- структурная и доменная валидация;
- детерминированная сортировка/read model;
- расчёт списка каскадов.

### Integration с PostgreSQL

- полный happy path команды и чтение результата;
- rollback всей команды при ошибке в середине;
- `expected_version`, конфликт двух клиентов и единственное увеличение версии;
- каскад без подтверждения и повтор с подтверждением;
- одновременное переименование двух сущностей с перестановкой уникальных имён;
- комбинированные каскады по нескольким типам связей;
- reload/второй клиент видят идентичное состояние.

### Frontend/E2E и архитектурные проверки

- экран визуально соответствует прототипу;
- одно действие порождает один write-запрос;
- успешный ответ полностью перерисовывает вкладку;
- offline/5xx не меняет сохранённые бизнес-данные;
- в browser storage нет PI business data;
- в активном bundle нет legacy-функций, демоданных и миграций;
- полный набор unit, integration и E2E проходит перед переносом шаблона.

## Definition of Done следующей вкладки

Вкладка считается выполненной по золотому стандарту, только если:

- у неё определены граница агрегата, команды, read model и каскады;
- все записи сохраняются в нормализованных backend-моделях;
- все пользовательские действия атомарны и защищены версией;
- frontend является проекцией backend и не содержит параллельной бизнес-модели;
- нет browser business storage, demo fallback и frontend migration;
- реализована полная матрица тестов;
- документация API и архитектурные contract-тесты не позволяют вернуться к
  прежнему подходу.
