# План доработки: авторизация, аутентификация и ролевая модель

## Цель

Добавить в приложение контур авторизации и ролевого доступа так, чтобы:

- пользователь без входа не видел приложение;
- после входа пользователь попадал на главную страницу выбора раздела;
- все авторизованные пользователи могли работать в доступных им разделах PI-цикла;
- доступ к вкладкам и действиям определялся ролью;
- на первом этапе роли назначались тестовым пользователям через `.env`;
- в будущем локальную проверку логина/пароля можно было заменить на LDAP/Active Directory без переписывания ролевой модели.

## Целевой пользовательский сценарий

1. Пользователь открывает приложение.
2. Если активной сессии нет, отображается экран входа.
3. Пользователь вводит тестовый логин и пароль.
4. Backend проверяет учетные данные через текущий auth-provider.
5. Backend создает сессию и возвращает пользователю доступные роли/права.
6. Пользователь попадает на главную страницу.
7. На главной странице доступны разделы:
   - `Бюджетирование` - пока не реализуется, отображается как будущий раздел;
   - `PI-цикл` - выбор года и квартала.
8. После выбора PI-цикла пользователь видит только вкладки, доступные его роли.

## Роли

| Роль | Код | Назначение |
|---|---|---|
| Администратор | `admin` | Полный доступ к системе, настройкам PI-цикла и управлению пользователями/ролями |
| Редактор планирования | `planning_editor` | Рабочая роль для LT / PO / ИТЛ; редактирует основные разделы планирования |
| Бизнес-наблюдатель | `business_viewer` | Роль для PM/заказчика; доступ только на просмотр к согласованным рабочим представлениям |
| Наблюдатель | `viewer` | Базовая роль авторизованного пользователя; просмотр доступных рабочих вкладок |

Роль `viewer` является базовой. В будущей LDAP-модели любой успешно вошедший пользователь без повышающих AD-групп должен получать `viewer`.

## Матрица доступа

| Раздел | `admin` | `planning_editor` | `business_viewer` | `viewer` |
|---|---|---|---|---|
| Данные PI-цикла | Редактирование | Вкладка скрыта | Вкладка скрыта | Вкладка скрыта |
| Бэклог команд | Редактирование | Редактирование | Вкладка скрыта | Просмотр |
| Pre PI Planning | Редактирование | Редактирование | Просмотр | Просмотр |
| Цели | Редактирование | Просмотр | Просмотр | Просмотр |
| Командные доски, включая емкость и задачи | Редактирование | Редактирование | Просмотр | Просмотр |
| Согласование задач | Может согласовывать любые задачи | Может согласовывать задачи | Нет | Нет |
| Program Board | Редактирование | Редактирование | Просмотр | Просмотр |
| Риски | Редактирование | Редактирование | Просмотр | Просмотр |
| Управление пользователями/ролями | Редактирование | Нет | Нет | Нет |

`Вкладка скрыта` означает, что раздел не отображается в интерфейсе. Прямой вызов API этого раздела пользователем без права доступа должен возвращать `403 Forbidden`.

## Важные ограничения

### Данные PI-цикла

Вкладка `Данные PI-цикла` доступна только администратору.

Только `admin` может:

- создавать и редактировать PI-циклы;
- задавать год, квартал, сроки и количество спринтов;
- настраивать трайбы, команды, типы команд и компетенции;
- редактировать справочные данные PI-цикла;
- управлять пользователями, ролями и будущим маппингом групп.

Остальные роли не должны видеть вкладку `Данные PI-цикла` и не должны иметь доступ к API ее чтения/редактирования.

### Выбор PI-цикла

После входа все роли попадают на главную страницу и выбирают PI-цикл по году и кварталу.

Для этого всем авторизованным пользователям нужен отдельный безопасный read-only endpoint навигации, который возвращает только минимальные данные для выбора:

- `id` PI-цикла;
- год;
- квартал;
- возможно статус или отображаемое название.

Этот endpoint не должен раскрывать содержимое вкладки `Данные PI-цикла`: сроки, команды, компетенции, состав PI и другие настройки доступны только администратору через отдельный admin-доступ.

## Рекомендуемые permissions

Роли лучше реализовывать через permissions, а не через проверки вида `if role == ...` в каждом endpoint.

## Аутентификация первого этапа

На первом этапе используется простая тестовая парольная авторизация.

Тестовые пользователи хранятся в `.env`, например:

```env
AUTH_ENABLED=true
AUTH_PROVIDER=local
SESSION_SECRET=change-me
SESSION_TTL_MINUTES=480

AUTH_TEST_USERS=admin:admin123:admin,editor:editor123:planning_editor,pm:pm123:business_viewer,user:user123:viewer

AD_GROUP_ADMIN=SBERPI_ADMIN
AD_GROUP_PLANNING_EDITOR=SBERPI_PLANNING_EDITOR
AD_GROUP_BUSINESS_VIEWER=SBERPI_BUSINESS_VIEWER
```

Формат `AUTH_TEST_USERS` можно уточнить при реализации. Важно, чтобы конфигурация позволяла быстро создать тестовых пользователей под каждую роль без миграций и ручного заполнения БД.

## Сессии

Рекомендуемый вариант для frontend-приложения - сессия через `HttpOnly` cookie.

Требования:

- cookie не хранится в `localStorage`;
- frontend отправляет запросы с `credentials: "include"`;
- backend проверяет сессию на каждом защищенном endpoint;
- logout завершает текущую сессию;
- при истечении сессии API возвращает `401 Unauthorized`;
- при недостатке прав API возвращает `403 Forbidden`.

На локальном этапе можно использовать подписанную cookie или серверные сессии. Для промышленного контура предпочтительнее серверные сессии, потому что их можно отзывать и аудитировать.

## API

Планируемые auth-endpoints:

| Endpoint | Назначение | Доступ |
|---|---|---|
| `POST /api/auth/login` | Вход по логину/паролю | Открыт |
| `POST /api/auth/logout` | Завершение сессии | Авторизованный пользователь |
| `GET /api/auth/me` | Текущий пользователь, роль, permissions | Авторизованный пользователь |
| `GET /api/app/navigation` | Главная страница: доступные разделы и PI-циклы для выбора | Авторизованный пользователь |

Защита существующих endpoints должна быть добавлена через FastAPI dependencies:

- `require_auth`;
- `require_permission("...")`;
- при необходимости `require_any_permission([...])`.

## Frontend

Frontend должен:

- показывать экран входа, если `/api/auth/me` возвращает `401`;
- после входа открывать главную страницу;
- отображать раздел `Бюджетирование` как будущий/недоступный раздел;
- отображать раздел `PI-цикл` с выбором года и квартала;
- после выбора PI-цикла показывать только вкладки, доступные текущей роли;
- скрывать вкладки без доступа полностью;
- скрывать или блокировать кнопки редактирования при отсутствии write-permission;
- корректно обрабатывать `401` и `403`.

Frontend-ограничения нужны для удобства пользователя. Основная защита должна быть на backend.

## Будущая LDAP/Active Directory модель

В будущем `AUTH_PROVIDER=local` должен быть заменен на `AUTH_PROVIDER=ldap`.

Целевая логика:

1. Пользователь вводит доменный логин и пароль.
2. Backend выполняет LDAP authentication.
3. Backend получает список AD-групп пользователя.
4. Backend сопоставляет AD-группы с ролями приложения.
5. Если пользователь успешно вошел, но не состоит в повышающих группах, он получает роль `viewer`.

Ожидаемый маппинг:

```text
SBERPI_ADMIN -> admin
SBERPI_PLANNING_EDITOR -> planning_editor
SBERPI_BUSINESS_VIEWER -> business_viewer
нет повышающих групп -> viewer
```

На первом этапе имена AD-групп задаются через `.env`. Позже при необходимости можно перенести маппинг в БД и добавить UI управления маппингом для администратора.

## Настройки LDAP на будущее

В `.env.example` можно заранее заложить параметры:

```env
LDAP_URL=ldaps://ad.company.local:636
LDAP_BASE_DN=DC=company,DC=local
LDAP_USER_SEARCH_BASE=OU=Users,DC=company,DC=local
LDAP_USER_FILTER=(sAMAccountName={username})
LDAP_GROUP_SEARCH_BASE=OU=Groups,DC=company,DC=local
LDAP_GROUP_FILTER=(member={user_dn})
LDAP_BIND_DN=
LDAP_BIND_PASSWORD=
LDAP_USE_TLS=true
```

Реальный LDAP-provider не реализуется на первом этапе, но архитектура должна позволять добавить его без изменения API и frontend-сценариев.

## План реализации

### Этап 1. Каркас авторизации

- Добавить настройки auth в `backend/app/core/config.py`.
- Добавить auth-сервис и локальный provider.
- Добавить endpoints `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`.
- Добавить сессионный механизм.
- Добавить тестовых пользователей из `.env`.

### Этап 2. Permissions и защита API

- Описать роли и permissions в одном backend-модуле.
- Добавить dependencies для проверки авторизации и прав.
- Закрыть write-endpoints по матрице доступа.
- Закрыть вкладку/API `Данные PI-цикла` только для `admin`.
- Проверить, что прямой API-доступ без прав возвращает `403`.

### Этап 3. Главная страница и скрытие вкладок

- Добавить главную страницу после входа.
- Добавить выбор раздела `PI-цикл`.
- Добавить выбор года и квартала.
- Добавить заглушку `Бюджетирование`.
- Скрывать вкладки и действия по permissions из `/api/auth/me` или `/api/app/navigation`.

### Этап 4. Тесты

- Добавить backend-тесты на `401` для неавторизованных запросов.
- Добавить backend-тесты на `403` для ролей без прав.
- Добавить тесты матрицы permissions.
- Добавить frontend contract-тесты на наличие auth-обработки и скрытие вкладок.

### Этап 5. Подготовка к LDAP

- Добавить интерфейс `AuthProvider`.
- Оставить `LocalAuthProvider` как текущую реализацию.
- Добавить каркас `LdapAuthProvider` без обязательного включения.
- Добавить env-настройки LDAP и AD-групп.
- Документировать переключение `AUTH_PROVIDER=ldap`.

## Нерешенные вопросы

- Нужно ли хранить историю входов и действий пользователя уже на первом этапе или отложить до отдельного аудита.
- Нужно ли добавлять статус PI-цикла (`draft`, `active`, `archived`) до внедрения авторизации или оставить выбор всех созданных циклов.
- Нужно ли `business_viewer` скрывать `Бэклог команд` окончательно или это временное ограничение матрицы.
