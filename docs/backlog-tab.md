# Архитектура вкладки «Бэклог»

## Граница агрегата

Общий бэклог — глобальный singleton-агрегат с версией `BacklogBoardState.version`.
Версия не связана с версией выбранного PI-цикла. В агрегат входят инициативы,
их UUID, Issue ID, бизнес-поля, теги, системы, исполнители, оценки и порядок.
PostgreSQL и backend — единственный источник истины.

## Read model

`GET /api/backlog-board?cycle_id={cycle_id}` возвращает:

- `version` и флаг инициализации;
- инициативы в каноническом порядке со стабильными UUID;
- стабильные UUID исполнителей;
- рассчитанную backend общую оценку `total_effort`;
- `cycle_id` контекста;
- справочники трайбов, команд и компетенций строго из `pi_cycle_teams` выбранного
  PI-цикла, а также справочник статусов.

Frontend хранит этот ответ только в памяти, отображает его в структуре прототипа и
хранит отдельно лишь фильтры и выбор активного трайба. Browser storage не содержит
инициатив, исполнителей, оценок или иных данных бэклога.

## Команды и optimistic locking

- `POST /backlog-board/items` — создать инициативу;
- `PATCH /backlog-board/items/{id}` — изменить одну инициативу;
- `DELETE /backlog-board/items/{id}` — удалить одну инициативу;
- `PUT /backlog-board/order` — сохранить один результат перетаскивания;
- `PUT /backlog-board` — атомарно сохранить всю форму;
- `POST /backlog-board/dispatch` — перенести серверную выборку в PI-цикл.

Каждая команда передаёт `expected_version`. Backend блокирует singleton-строку,
сверяет версию и увеличивает её ровно один раз. Ошибка откатывает всю транзакцию.
После успеха API перечитывает и возвращает полный read model; frontend заменяет им
предыдущий ответ и повторно строит экран. При `version_conflict` запись автоматически
не повторяется.

## Валидации и каскады

Backend нормализует и проверяет Issue ID, обеспечивает регистронезависимую
уникальность, проверяет включение трайбов и команд в выбранный PI-цикл, принадлежность
владельца трайбу, уникальность исполнителей, настроенные в этом цикле компетенции и
неотрицательные конечные оценки.
Статус отправки может установить только команда переноса. Порядок строк и
исполнителей хранится серверно.

`dispatch` сам выбирает инициативы по трайбу, году и кварталу, блокирует целевой
PI-цикл, проверяет его команды и компетенции, создаёт/обновляет PI-копии и увеличивает
версии обоих агрегатов в одной транзакции. Повторная команда синхронизирует уже
связанные PI-копии по стабильному `backlog_item_id`, не создавая дубликаты. Она
обновляет Issue, название, описание, продукт, владельца, тип, размер майки,
приоритеты, теги и ресурсы владельца, но сохраняет цель, метрику, AS IS/TO BE,
гипотезу, редизайн, положение в Pre PI и запросы на привлечение. Конфликтующий
перенос отклоняется без частичного результата.

Удаление отправленного источника сначала возвращает
`409 cascade_confirmation_required`. Повтор с `confirm_cascade: true` разрывает
ссылки на независимые PI-копии и увеличивает версии затронутых PI-циклов атомарно.

## Legacy

Удалены frontend-снимок `state.tribeBacklog`, демопосев бэклога, debounce/autosave,
локальное вычисление общей оценки, frontend-перенос в Pre PI, старые `/backlog`,
PI-scoped `backlog/dispatch` и `/initiatives/from-backlog`.
