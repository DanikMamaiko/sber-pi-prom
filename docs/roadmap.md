# Roadmap реализации

## Этап 1. Текущий каркас

- Создан новый репозиторий.
- Заложены FastAPI, Postgres и vanilla frontend.
- Описана доменная модель PI-цикла.
- Реализованы базовые API для PI-циклов, трайбов, команд, бэклога, инициатив, целей и рисков.
- UI позволяет пройти первый ручной поток без Jira.
- Хранение PI-циклов подключено к FastAPI/Postgres с безопасным импортом старой сессии.
- Вкладка «Данные PI-цикла» перенесена в нормализованный транзакционный setup API.
- Вкладка «Бэклог команд» перенесена в Postgres: агрегатное сохранение, безопасный
  импорт старой сессии и атомарная отправка/повторная отправка в Pre PI.
- Вкладка «Pre PI Planning» перенесена в нормализованные Initiative: поля
  инициатив, порядок блоков, исполнители, оценки и привлечение сохраняются через API.
- Вкладка «Цели» и действие «Отправить на доски» перенесены в backend:
  серверная валидация, транзакционная публикация и идемпотентная повторная отправка.
- Содержимое командных досок перенесено в Postgres: размещение инициатив, stories, белые подзадачи,
  порядок стикеров и согласование сохраняются транзакционно и восстанавливаются через API.
- Состав и ёмкость команд перенесены в Postgres: backend рассчитывает календарную и доступную
  ёмкость по спринтам и компетенциям и сопоставляет её с планом инициатив Pre PI.
- Связи Program Board и их геометрия перенесены в Postgres: endpoints нормализуются до UUID
  инициатив и работ, а frontend сохраняет и восстанавливает линии через отдельный API.
- Общие и командные риски перенесены в Postgres: команда проверяется в контексте PI-цикла,
  а общий командный риск зеркально отображается без создания дублирующей записи.
- Схема БД переведена на Alembic.
- Выполнена сквозная API/UI-регрессия всех вкладок PI-цикла; проходит 21 pytest-тест,
  включая 5 интеграционных сценариев на отдельном PostgreSQL 16.
- Выполнен релиз A удаления compatibility snapshot: запись отключена, старое содержимое
  сохранено как read-only fallback, созданы полный dump и JSON-экспорт.
- Выполнена техническая часть релиза B: frontend не читает snapshot и старую сессию,
  write API отклоняет поле snapshot с 422, `STORAGE_VERSION` повышен до 4.
- Выполнен релиз C: миграция `20260728_0009` удалила колонку snapshot; поле удалено из
  SQLAlchemy, Pydantic и OpenAPI, данные проверены на чистой и существующей БД.
- Миграцией `20260728_0010` добавлен optimistic locking: общая версия PI-цикла и отдельная
  версия глобального бэклога, 409 при конфликте и последовательная очередь сохранений frontend.

## Этап 2. Довести MVP до пилота

- Добавить импорт/экспорт данных для пилотного заполнения.
- Добавить браузерные smoke-тесты в CI.

## Этап 3. Подготовка к промышленной эксплуатации

- Авторизация и роли.
- Аудит действий.
- Jira/JSW-интеграция.
- Нотификации и согласования.
- CI/CD.
- Наблюдаемость: логи, метрики, health checks.
- Резервное копирование Postgres.

## Этап 4. После PI-cycle MVP

- Вернуть модуль бюджетирования как отдельный bounded context.
- Связать бюджетные оценки с инициативами PI.
- Добавить финансовые статусы, Vadarod/Vendor-модели и бюджетные отчёты.
