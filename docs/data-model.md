# Модель данных PI-цикла

## Справочники

`Tribe`

- `id`
- `name`

`Team`

- `id`
- `tribe_id`
- `name`
- `team_type`: `Agile` или `IT_PROJECT`
- `excluded_from_goals`

`TeamCompetency`

- `team_id`
- `code`: `SA`, `DEV`, `QA`, `FE`, `BE`, `DES` или другой код
- `sort_order`

`TeamMember`

- `team_id`
- `full_name`
- `competency`
- `rate`
- `unavailable_ranges`
- `ceremony_percent`
- `risk_percent`
- `efficiency_percent`

## PI-цикл

`PiCycle`

- `year`
- `quarter`
- `start_date`
- `sprint_count`
- `status`
- `version`: общая версия optimistic locking для всех агрегатов этого PI-цикла;
- флаги `setup/initiatives/goals/boards/capacity/program_board/risks_initialized` для
  различения нового и корректно пустого агрегата.

`PiEvent`

- `cycle_id`
- `name`
- `event_date`

`PiCycleTeam`

- связывает глобальную команду с конкретным PI-циклом;
- хранит порядок, тип команды и признак исключения из целей для этого цикла.

`PiCycleTeamCompetency`

- хранит выбранные компетенции команды внутри конкретного PI-цикла.

`PiCycleCapacityMember`

- участник команды и его параметры ёмкости внутри конкретного PI-цикла;
- хранит стабильный `client_uid`, компетенцию, ставку, отпуск и дополнительные периоды
  недоступности, проценты церемоний/риска, КПД и порядок строки;
- календарная и доступная ёмкость рассчитываются backend по рабочим дням каждого спринта.

`PiCycleGoalOption` и `PiCycleTag`

- упорядоченные справочники целей и тегов конкретного PI-цикла.

Спринты пока вычисляются от `start_date` и `sprint_count`, длительность одного спринта - 14 дней.

## Бэклог

`BacklogItem`

- ручная замена Jira issue в MVP;
- хранится вне конкретного PI-цикла;
- связан с трайбом и хранит порядок строки внутри трайба;
- хранит квартал/год реализации, приоритеты, продукт, тип, системы АС, статус и
  историю целевых PI-циклов;
- может быть перенесён в один или несколько PI-циклов как `Initiative`.

`BacklogExecutor`

- команда-исполнитель;
- `effort_by_competency`: словарь вида `{ "SA": 3, "DEV": 8 }`.

`BacklogBoardState`

- singleton-маркер первого импорта;
- хранит отдельную `version` optimistic locking глобального бэклога;
- позволяет отличить ещё не импортированную доску от корректно пустой и не
  восстанавливать удалённые строки из старого `sessionStorage`.

## Инициативы PI

`Initiative`

- конкретное попадание бэклог-элемента в PI-цикл;
- содержит поля Pre PI: цель/веха, метрика, AS IS, TO BE, гипотеза, редизайн;

### InitiativeAttraction

Нормализованный запрос на привлечение (`initiative_attractions`) принадлежит
`InitiativeExecutor` и ссылается на целевую `Initiative` и `Team`. Хранит стабильный
UUID, `sprint_index`, `approval_status` и `sort_order`. Уникальность цели в рамках
исполнителя защищает от дублей; self-reference и принадлежность PI-циклу проверяет
доменный сервис. Прежний JSONB `initiative_executors.attractions` сохранён только
для безопасного аудита исторических повреждённых значений и активным кодом не
используется.
- имеет статус: `backlog`, `planned`, `on_board`, `done`;
- может быть размещена на спринте через `sprint_index` и `week_index`.

`InitiativeExecutor`

- исполнители и трудозатраты по компетенциям внутри PI.

`Story`

- слой историй между инициативой и рабочими задачами.
- имеет стабильный `client_uid`, внешний ID, оценку по компетенциям, спринт/неделю и порядок на доске.

`WorkItem`

- белая подзадача/работа;
- связана с инициативой и опционально с историей;
- содержит стабильный `client_uid`, серверную ссылку `assignee_member_id` на участника
  ёмкости активного PI, отображаемое ФИО, компетенцию, трудозатраты, спринт, неделю и
  порядок на доске;
- удаление участника ёмкости очищает назначения только после явного подтверждения каскада.

## Цели

`PiGoal`

- цель на уровне PI, трайба или команды;
- может быть связана с инициативой;
- хранит метрику, AS IS, TO BE, продукт, гипотезу и редизайн.

## Program Board

`BoardConnection`

- направленная связь между инициативой и/или белой работой внутри одного PI-цикла;
- `source_kind/source_id` и `target_kind/target_id`, где `source_id` и `target_id` — UUID
  нормализованных `Initiative` или `WorkItem`;
- стабильный frontend-идентификатор `client_uid` и backend UUID `id`;
- тип связи по умолчанию `depends_on` и порядок `sort_order`;
- геометрия линии `bend_dx`/`bend_dy` — смещение точки изгиба относительно середины endpoints;
- уникальность `client_uid` внутри цикла; петли и дубли одинаковых направленных связей запрещены.

API принимает frontend-ссылки `{kind: "c", ref: issue_key}` и
`{kind: "w", ref: work_item.client_uid}`, разрешает их в UUID и удаляет связь при удалении
любого endpoint. Так UI сохраняется без дублирования доменной связи в браузерном состоянии.

## Риски

`Risk`

- `scope`: `general` или `team`;
- `team_id`: UUID нормализованной `Team`, входящей в текущий PI-цикл; заполнен только для
  командного риска;
- стабильный frontend-идентификатор `client_uid`, backend UUID `id` и `sort_order`;
- `is_shared`: командный риск зеркально отображается в общих без создания второй записи;
- описание, владелец, влияние, контрольная точка и план работы;
- `client_uid` уникален внутри PI-цикла, а весь набор сохраняется одной транзакцией.

При удалении команды из setup её командные риски удаляются. Маркер `risks_initialized`
отличает новый агрегат от корректно инициализированного пустого набора.
